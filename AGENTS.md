# AGENTS.md

## Project

`rdmalib` — one crate, Rust 2024 edition, **zero dependencies by design**: the RDMA FFI is hand-written, do not add `*-sys` crates. Layout:

- `src/lib.rs` — high-level API: client side (`RemoteMemoryProvider`), server side (`SharedMemoryRegionProvider`). Must stay free of verbs specifics.
- `src/meta.rs` — the metadata channel: the TCP wire protocol (framing + messages) and `Channel`, plain `std::net` — the zero-dependency TCP choice, deliberate. No RDMA knowledge; both high-level sides drive it.
- `src/rdma/` — low-level RDMA (`verbs.rs`: libibverbs + rdma_cm FFI). Confined to its own module so the implementation can be swapped for a different technology; `rdma/mod.rs` is the re-export seam.
- `old_cpp_lib/` — older C++ implementation of the same ideas; read for semantics (`conn.cpp`, `remote_process/ops.cpp`), but it does more (TCP sync, pre-allocated buffers) — don't copy blindly.
- `src/tests/` — **inner tests**, agent-owned: unit tests and small tests that run locally, in the container, without RDMA hardware (they may use private internals; not `tests/`). Run them to verify changes, modify them freely. Anything that needs a real node — the full flow over RDMA, HPC runs — is an **outer test** and belongs in `tests/`, never here.
- `tests/` — **outer tests**: cluster integration tests (public API only), deployed to real nodes by `scripts/test_runner.py` (see below). `tests/common/mod.rs` is the shared helper module, `tests/_test_config.json` the machine-specific cluster config. **User-owned**: for humans only — do not execute or modify them unless explicitly asked.

## Commands

- Host fast loop (no linking, always works): `cargo check`, `cargo clippy --all-targets`.
- Run the unit tests (`src/tests/`): `./podman_build/link_test.sh [cargo-test-args…]` (e.g. `…/link_test.sh verbs_struct` for one test). Uses **podman, not docker**; builds/reuses the `rdmalib-dev` image from `podman_build/Containerfile`.
- The dev host has **no RDMA stack**: no librdmacm at all, a truncated runtime-only `libibverbs.so.1`, no `/dev/infiniband`, no root. Plain `cargo test` on the host fails to link — that is expected; don't try to fix it, run tests through the script.
- Hardware-dependent tests are `#[ignore]`-gated and meant for the remote HPC (`cargo test -- --ignored` there). Local and container runs must stay green without hardware.
- Edition 2024 needs rustc >= 1.85 — that's why the Containerfile installs rustup instead of the distro rustc.

## Cluster integration tests (`tests/`)

- **Ownership**: these are the user's tests. Do not execute them — never forward `--ignored`/`--include-ignored`, that is the runner's deploy trigger — and do not modify anything under `tests/` unless explicitly asked. Verify changes with the `src/tests/` unit tests (`link_test.sh` without the flag) instead.

- `.cargo/config.toml` routes **every** test binary through `scripts/test_runner.py`. A binary listed in `tests/_test_config.json` (key = test name, e.g. `read_test`) is a cluster test: the runner rsyncs the binary to that test's nodes and launches it on all of them concurrently over ssh, streaming per-node output. Everything else — the lib unit tests, or a cluster test when no `--ignored`/`--include-ignored` flag was forwarded — is exec'd locally, untouched: that is what keeps plain `cargo test` / `link_test.sh` green (and working at all) on machines without a cluster.
- Cluster tests are `#[ignore]`-gated (they need RDMA hardware); run one via `./podman_build/link_test.sh --test read_test -- --ignored` — the flag both selects them and is the runner's deploy trigger. In that mode the container is only the *builder* (`cargo test --no-run`, artifacts persisted under `target-cluster/`, gitignored) and `scripts/test_runner.py` then runs **on the host**: the container has no ssh config/keys for the node hostnames, the host does. Without `--test <name>`, every cluster test in the config is deployed.
- The runner passes the layout to each remote process via env vars: `RDMALIB_TEST_NODES` = comma-separated `ip:tcp_port:rdma_port` (one per deployed node, ports = `base_ports` + position, IPv4 only) and `RDMALIB_TEST_MY_NODE` = that process's index into the list. `tests/common/mod.rs` parses them (`TestCluster::from_env()`) and builds provider/reader addresses per node. Deployed runs get `--nocapture` appended automatically: libtest otherwise captures (and drops) the stdout of passing tests, and the whole point of deploying is streaming the nodes' output.

## FFI rules (`src/rdma/verbs.rs`)

- No verbs headers exist on this host: verify layouts/constants against upstream rdma-core headers (`libibverbs/verbs.h`, `librdmacm/rdma_cma.h` on GitHub) instead of trusting memory.
- Known traps already hit: `ibv_post_send`/`ibv_poll_cq` are `static inline` in `verbs.h` (NOT library symbols) — they dispatch through `ibv_context->ops` (`post_send` at index 25, `poll_cq` at 11); `struct ibv_mr` has a `handle` field before `lkey`/`rkey`; `IBV_SEND_SIGNALED = 1<<1` (`IBV_SEND_INLINE = 1<<3`); `RDMA_PS_TCP = 0x0106`; `rdma_create_qp`'s init attr is **in/out** — the driver writes the granted `cap.max_inline_data` back into it (both libibverbs' create path and the providers, e.g. mlx5's `mlx5_calc_sq_size`, do), which is how the connection's inline budget is discovered — probing descending candidates on create failure, no `ibv_query_qp`/`ibv_query_device` needed.
- The inline probe's top candidate (`INLINE_CANDIDATES` in `verbs.rs`) is mlx5's ceiling, 924: `mlx5_calc_send_wqe` fits a send WQE in the device's 976-byte `max_sq_desc_sz` in 64-byte blocks — asking 924 builds a 960-byte WQE and grants 924 back (960 − 36 control/remote-address/inline header bytes); asking 220 grants exactly 220. Keep the top candidate at the device ceiling: a lower one reads back normally on the wire, and every size between it and the ceiling silently takes the staging pool instead of the inline path.
- Memory-window traps: `ibv_bind_mw`/`ibv_alloc_mw`/`ibv_dealloc_mw` are `static inline` in `verbs.h` (NOT library symbols) — `alloc_mw`/`dealloc_mw` null-check and dispatch through the ops table (entries 7/9), while `bind_mw` (entry 8) only *validates* and dispatches: **the bind is asynchronous** — the call posts the WR and returns, the bind takes effect at its CQE (which carries `mw_bind->wr_id`), and the verbs contract is: the posted bind eagerly writes the *next* rkey into `mw->rkey`, which must be restored on a failed completion, and the new rkey must not be handed to a remote before the completion. `Connection::bind_mw`/`unbind_mw` wrap exactly that: post, `wait_completion`, rkey forward only on the CQE, restore on failure. `struct ibv_mw` puts `rkey` at offset 16, *before* `handle`/`type` (counterintuitive vs `ibv_mr`); the rkey rotates in its low 8 bits only (`ibv_inc_rkey`), so one window cycles 256 keys — never resurrect an old binding's key within a run. The zero-length bind (`unbind_mw`) is the revoke: from its completion no access under the previous binding is served, in-flight requests included (IBA C10-67/C10-68 — this is the completion-linearized revocation `providers.rs` exposes as `revoke_region`). **A bind's target MR must be registered with `IBV_ACCESS_MW_BIND` (1<<4)** — the migration of the old experimental `IBV_EXP_ACCESS_MW_BIND`, and the one hard requirement the man pages bury: a bind over an ordinary registration completes with `IBV_WC_MW_BIND_ERR` ("memory management operation error"; CX-3 Pro reports vendor syndrome 94) *and sends the posting QP to ERROR* (everything after it flushes, vendor 0xF9 = 249) — while `ibv_alloc_mw` succeeds all the same, so allocation proves nothing about bind permission. `ProtectionDomain::register_window_target` exists for window backings; the values are pinned in `verbs_constants`. `WINDOW_ACCESS` grants **read+write only**: nothing served through windows uses atomics, and a bind is a grant against what the port can serve — a RoCE port carries no atomic operations, unlike a plain registration, which merely records the flags and lets the ops fail at use time.
- Completion-status traps: the `enum ibv_wc_status` values are NOT what memory suggests — `IBV_WC_WR_FLUSH_ERR = 5` and `IBV_WC_REM_ACCESS_ERR = 10` (the obsolete `LOC_EEC_OP_ERR` at 3 shifts everything). `verbs.rs` classifies exactly these two (see `CompletionStatus`) — anything else is `Other`, and the classification is what `is_remote_access`/`is_flushed` match on.
- The Rust structs mirror only the leading C fields; the tests at the bottom of `verbs.rs` pin sizes/offsets with `offset_of!` — keep them in sync when touching the mirrors.
- Dead-stripping can hide link errors: an FFI typo only surfaces when a test actually calls the path.

## Design invariants (don't "simplify" these away)

- A **group id identifies a set of readers with the same access**: one binding per (region, group), so every reader in a group shares one rkey — and a group can be granted and revoked as a unit. Bindings are created lazily per (region, group) in `get_shared_mr` (as before) but now *live in the group entry*, not a separate map: a window operation is a bind WR posted through one of the group's connections with its completion awaited, and putting the binding, the connections, and the PD under the groups lock together means the operation holds exactly one lock — the never-nested rule survives revocation by construction. A region marked `serve_through_windows` gets a type-1 window binding per group instead of a registration — its backing is registered as a **window target** (`register_window_target`: the `IBV_ACCESS_MW_BIND` permission binds demand of their target; a bind over an ordinary registration fails its CQE and kills the posting QP); its tuple serves the window's rkey (the backing registration's rkey is never served), `revoke_region` binds it to zero length — returning only after the completion, the point from which no access under the previous binding is served (IBA C10-67/C10-68) — and `grant_region` rebinds the full range under the rotated fresh rkey. A revoked group keeps being served its (dead) rkey, so its operations fail *classifiably* (`is_remote_access`) instead of the region vanishing from its catalog; the fresh rkey travels with the next tuples re-request. A bind through a failed QP flushes and leaves the previous binding standing — `bind_through` walks the group's connections newest-first for exactly that, and a group with no live connection cannot post: its revocation defers until one exists (the caller's confirmation protocol must allow the wait).
- **A revocation reaches the consumer as TWO completion flavors, then the flush** — classify both, or a consumer dies on the rarer one. The window bind that revokes (zero-length, C10-68) commits while the consumer's operations may be in flight on the same queue pair from the other end: an operation whose rkey check ran after the bind is refused as `IBV_WC_REM_ACCESS_ERR` (remote access error — the common flavor, and the only one early runs ever saw), while an operation the check had already admitted is aborted mid-flight as `IBV_WC_REM_OP_ERR` (remote operation error — the rare, timing-dependent flavor; it first surfaced only after the permission agent's poll interval dropped to 200 µs, shifting the collision odds enough to land one). Both error the requester's queue pair, whose remaining work then reads as `IBV_WC_WR_FLUSH_ERR`. That is why `is_remote_access`/`is_remote_op`/`is_flushed` are three separate classifiers: the consumer's policy composes them into one no-permission verdict.
- Groups are implemented with a **shared per-group protection domain** (`rdma::ProtectionDomain`, `Listener::accept_into`): all of a group's connections create their QPs in it, so one registration per (region, group) serves every reader of the group, and a group's *windows* work through any of its QPs — which is what makes revoke/grant possible from a connection other than the one the bound rkey was served over. Verbs rkeys only work through QPs in the PD the memory was registered in — that is why the domain, not the connection, owns registrations and windows.
- Tuple creation must **not touch the buffer** (the app may hold a `borrow_mut`): that is why registration uses `ProtectionDomain::register_addr(addr, size)` with the address captured at `register()` time, not a slice. Buffers are never resized after registration — the handle API only exposes slices. The provider's state is split accordingly: `Shared` (catalog of plain `RegionInfo` data + groups + tuples, `Arc<Mutex<…>>`) is shared with the service thread, while the buffer owners (`owners`, `Rc`) stay confined to the application thread.
- A **session** pairs one TCP connection with one RDMA connection: reader sends `Hello`, then `WantGroup { group }`, then connects over RDMA **announcing the group in the connect's private data**; the provider accepts it into the group's PD (creating the group on first use) **matching the announced group against the session's** (`Connection::connect_group` / `Listener::accept_group_into`: a stale or out-of-order request — another recovery's, whose exchange failed after it connected — is *rejected and released*, never wired into the wrong group's PD, where its reader's rkeys would not resolve at all) and replies with the catalog + the group's tuples. Group membership is **reader-declared** (v1; owner-side group policy remains future work — per-region windowing and revoke/grant are the owner's *actions*, the policy of who may join is not). The reader keeps the TCP channel open; `update(group)` re-requests over it, or opens a fresh session if the exchange failed; **`reconnect(group)` forces the fresh path** — dropping the channel so the next update re-runs the handshake and *replaces the RDMA connection* (the recovery for a group whose QP has failed, which a healthy channel would otherwise never heal: refresh never touches the connection). Each group has its **own RDMA connection** on the reader side (rkeys only work through QPs in the group's PD — a single shared connection was a latent multi-group bug). An exchange the provider **cannot** serve — a region's tuple that fails to materialize, e.g. a windowed region whose bind the device refuses — is answered with `ServeError` (carrying the reason) and the session closes: a region is never silently omitted from the tuples, which would surface later as a causeless "no tuple" after a session that looked successful.
- **The listener's event channel is shared with every connection it accepted**, and connection churn lands on it: replacing a connection (recovery's fresh session) drops the old one, whose `rdma_disconnect` the peer reports as a `DISCONNECTED` event *on that channel* — and concurrent recoveries mean disconnects arrive while later rendezvous are accepting. The accept path therefore **drains every event that is not its own connection request** (acknowledged, never failed on) and **bounds both its waits** (request and establishment, `CM_EVENT_TIMEOUT` via `poll` on the channel fd): treating churn as an error kills an unrelated handshake mid-session (the reader sees `read_exact` EOF: "failed to fill whole buffer"), and an unbounded accept wedges the *serial* session service forever — one reader that sent `WantGroup` but never connected stalls every later reader behind it. `bind_through` prunes a connection whose post *flushed* (provably dead) instead of retrying it on every later window operation.
- **The TCP accept must wait *on the listener's fd*, never a fixed sleep**: the loop stays non-blocking only so shutdown can be checked, but its wait is `poll` on the listener (waking the instant a connection arrives), with `SERVICE_POLL` bounding only the shutdown check. A `sleep(SERVICE_POLL)` between failed accepts instead prices *every* fresh rendezvous up to the interval — invisible at startup, but a mid-run recovery's fresh session (whose consumer is blocked reading `Welcome`) then sits in the backlog for up to 100 ms while the experiment's writer keeps going; with revoke/grant in play this surfaced as a reader frozen mid-recovery for the length of a whole run and a barrier stalled ~96 ms on binds with no live QP to post through.
- **The metadata channel must be `TCP_NODELAY`** (`Channel::new`, the one constructor both sides adopt their streams through): the protocol's exchanges are bursts of small back-to-back frames — the catalog, then the tuples — with the peer blocked in `receive` in between, which is Nagle's worst case. Nagle holds the second frame for the first one's ACK, and a blocked receiver has nothing to piggyback that ACK on, so its stack sits on it for the delayed-ACK timer (~40 ms on Linux): one timer per exchange, invisible as a slow *startup* but paid twice by a mid-run recovery (the fresh session, then the tuples re-request that carries the fresh rkey). Signature: every fresh session ~45 ms, recoveries ~90 ms with both `update` phases slow and the RDMA-only phases (the agent-mediated restore) sub-millisecond — and every consumer paying it *in parallel*, which distinguishes the stall from the serial session service queueing.
- The remote side connects **lazily on the first `update(group)`**, so `RemoteMemoryProvider::new` stays infallible and tests run without hardware; region reads and writes go through the group's connection slot and fail (not panic) when no session has run.
- Threading stance: the verbs handles are `Send` (not `Sync`; `ProtectionDomain` moved from `Rc` to `Arc` and `PdInner` is `Send + Sync` with a documented safety argument) so `Shared` can cross threads; the `Arc<Mutex>` locks are taken one at a time, **never nested**. The service thread owns both listeners and runs the **rendezvous serially** (an `rdma_cm` listener cannot be shared across session threads without connection-pairing logic); each open session's update-wait runs on its own thread. This is also what keeps future CPU pinning viable: all library work stays on library-owned threads.
- Drop order matters: `Drop for SharedMemoryRegionProvider` stops the service first (shutdown flag + join — the accept loop is nonblocking/polled because closing a listener does not wake a blocked accept on Linux), then clears the tuples map, so ibv registrations are deregistered before their connections (PDs) are destroyed; don't reorder fields/teardown.
- Typed sharing (`register_typed`, typed handle borrows, `read_typed`) goes through the **`RemoteSafe` unsafe trait** (`src/pod.rs`): the implementer asserts every bit pattern is a valid `T` (`#[repr(C)]`, no bool/char/enums/refs — remote writers produce arbitrary bytes). Buffers are stored **type-erased** (`Rc<RefCell<Box<dyn Any>>>`, shared entry↔handle) and borrows downcast to `&[T]` — never transmute the `Vec` itself (wrong-layout dealloc). Verbs only ever sees the byte (addr, size) captured at registration. The element layout (size, alignment, type name) travels with the catalog and `read_typed`/`write_typed` reject a mismatched `T` — a **layout** check only; type identity between the separately compiled sides remains the user's responsibility. Reader-side typed reads and writes also check bounds and remote-address alignment before the device is touched. Writes are one-sided RDMA writes through the same group connection and rkey as reads (regions are registered with remote-write access).
- **Reader-side data operations never register memory per call** (registration is kernel round trips + page pinning, ~10–100 µs against ~2 µs of wire time; this is the library's whole latency story). The paths: unregistered reads/writes bounce through the group connection's **staging pool** (`Staging` inside `GroupConnection`, created lazily at the pool capacity the provider configured — 1 MiB default, parametric via `with_staging_capacity`/`set_staging_capacity`, chunks of `min(capacity, remaining)` per WR — never resized after registration pins it), small writes ≤ the connection's inline budget post straight from the caller's memory (`IBV_SEND_INLINE`), and **`RegisteredBuffer`** (registered once in the group connection's PD by `register_buffer[_typed]`) is the zero-copy path. The staging pool is declared before the connection field so its MR deregisters while the connection's PD is alive; the engines take raw pointers (`read_into_ptr`/`write_from_ptr`) with the caller holding the RefCell borrow and SAFETY contracts on the pointer spans.
- **A connection replacement (fresh session in `update`) replaces the group's PD**: the staging pool is dropped first (registered in the old PD), `generation` is bumped, and each `RegisteredBuffer` re-registers on its next use (it stamps the generation it registered under). This is sound because **`rdma::MemoryRegion` keeps its `ProtectionDomain` alive** (holds an `Arc` handle of it, PD identity checked with `Arc::ptr_eq`): a registration may outlive its connection — the old PD stays alive until the stale MR's `Drop` deregisters it (rdma_cm device contexts are process-global). Don't revert that to a raw PD pointer; it is what makes re-registration and the provider's tuples-vs-connections teardown order safe.

## Not implemented yet

Owner-side group policy (membership is reader-declared; windowing and revoke/grant are the owner's actions but not a join policy), reaping of dead reader connections proactively (today `bind_through` prunes a flushed one on the next window operation — no event-driven cleanup), IPv6, atomic verbs, async post+poll reads and writes.
